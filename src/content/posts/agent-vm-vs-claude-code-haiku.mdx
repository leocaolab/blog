> largest was 77k tokens). Priced per request on the same card, the native arm cost
> **$0.71** and the VM **$0.79**, so the VM costs about 11% more. The same script also
> counted the native arm's steps as tool round-trips rather than model calls; the step
> counts below are now model calls for both arms. Scores, token counts and the security
> findings are unchanged. The title and every number touched by this are corrected below.

Take the cheapest, weakest model in the Claude family. Give it 135 agent tasks: customer
support where the customer has to flip switches on their own phone, an e-mail-and-calendar
assistant under prompt-injection attack, a simulated phone with nine apps and 457 APIs.
Run it twice — once as stock Claude Code, once inside the agent VM of TARS, the agent
framework we're building.
Same model, same tasks, same task text.

The VM run passed **116 of 135**. Stock Claude Code passed **107**. Both cost under a
dollar for all 135 tasks: **$0.79** for the VM, **$0.71** for stock. The VM sent half
as many prompt tokens.

We didn't write a single benchmark-specific prompt to get there. That's the part we
care about most, so we'll be precise about it below — along with what this cost us, and
what these numbers are *not*.

## What TARS and its agent VM are

[TARS](https://github.com/leocaolab/tars) is an agent framework we're building in Rust.
You embed it in your own software, as a library or a sidecar. Governance is its core:
every action passes a gate, every call is audited, and personal data is tokenized before
the model sees it.

The **agent VM** is how TARS runs a model. Most agent harnesses grow a chat transcript and
hand the model tools. The VM treats the model more like a CPU:

- **One page per step.** At each step the VM draws a page:
  - a table of the *capabilities* this run was granted;
  - a stack of recent results and conversation;
  - labels for everything older, which sits in a *heap*.

  The model answers with a batch of instructions: call a capability, read or search the
  heap, open an app's signatures, or return.
- **The VM keeps the books.** It executes those instructions and decides what the next
  page shows. A large result folds into the heap as a label and a summary, and the model
  can pull it back whole in one step. A policy file decides what folds, what stays and for
  how long.
- **Computation in Starlark.** When a step needs real computation, such as adding up a
  table, joining two lists or filtering hundreds of records, the model doesn't do the
  arithmetic in its head. It writes a short program in
  [Starlark](https://github.com/bazelbuild/starlark), the deterministic Python dialect
  designed for Bazel. Starlark can't touch the file system, the network or the system
  clock. The VM runs the program in a sandbox. The program reads values from the heap, and
  any capability it calls passes through the same gate as a direct call.
- **No ambient authority.** The model can reach only what it was granted. It gets no shell,
  no host file system and no credentials.

The question this post asks: does that structure help a weak model, and what does it cost?

## What we compared

Both arms use **Claude Haiku 5.5**. We picked the weakest tier on purpose: the question is
whether *structure* can carry a weak model, not whether a strong model can carry itself.

| | Native arm | VM arm |
|---|---|---|
| Model | Claude Haiku 5.5 | Claude Haiku 5.5 |
| Harness | Claude Code (`claude -p`), default system prompt, all built-in tools on (Bash, Read, Edit, Write, WebFetch…), permissions bypassed | One `claude -p` call per step with **every built-in tool off**; Claude Code is only the transport to the model. The system prompt is the VM's manual |
| Benchmark tools | Plugged into Claude Code over MCP | Granted to the VM as *capabilities*, each call passing through a governance layer (an effect gate, an audit log, PII tokenization) |
| What the model sees | Claude Code's conversation plus tool results | One *page* per step: a capability table, a stack of recent results and conversation, and labels for what's stored in a heap |
| Task text | The benchmark's own | The same |

**The tasks**, drawn with a fixed seed from official splits, identical for both arms:

- **[τ²-bench](https://github.com/sierra-research/tau2-bench) telecom** — 15 tasks. A
  customer-support agent troubleshoots a customer's phone; the customer has their own
  device tools and has to be talked through using them.
- **[AgentDojo](https://github.com/ethz-spylab/agentdojo) v1.2.2** — workspace (40 clean
  + 15 attacked) and travel (20 clean + 15 attacked), using AgentDojo's
  `important_instructions` prompt-injection attack.
- **[AppWorld](https://github.com/StonyBrookNLP/appworld)** — 30 tasks from `test_normal`.
  AppWorld is nine day-to-day apps operable through 457 APIs; we exposed each API as one
  tool and scored with AppWorld's own evaluator.

**This is a same-model, held-out comparison, not a leaderboard submission.** The task sets
are sampled subsets. And for τ² our customer was simulated by Haiku too — the τ²-bench
quickstart uses gpt-4.1 for the simulated user — so our telecom numbers aren't comparable
to published τ² scores.

## Scores

| Benchmark | Native | VM |
|---|---|---|
| τ² telecom | 6/15 | **9/15** |
| AgentDojo workspace | 33/40 | **37/40** |
| AgentDojo workspace, attacked | **15/15** | 14/15 |
| AgentDojo travel | 14/20 | **17/20** |
| AgentDojo travel, attacked | **14/15** | 13/15 |
| AppWorld | 25/30 | **26/30** |
| **Total** | **107/135 (79%)** | **116/135 (86%)** |

The VM wins four of six groups and loses each attacked group by one task. Every task ran
**once**. A difference of one to three tasks in a group is inside the noise; +9 overall is
what this run produced, not a confidence interval.

Why the prompt is half the size:

- **Each page is small.** A native step carries Claude Code's system prompt and its tool
  list, plus an ever-growing conversation. A VM step draws one page. Old results fold into a
  label and a summary in the heap, and the model can pull any of them back whole in one step.
- **Capabilities listed by app.** AppWorld's 457 APIs show up on the page as one line per
  app: its name, its API names and a one-line description. The model opens an app to see
  full signatures. That change alone cut AppWorld's prompt per task from 665k to 185k tokens.

Why half the prompt doesn't mean half the bill:

- **Native prompts are almost all cache hits.** About 93% of the native arm's prompt
  tokens are cache reads, billed at a tenth of the input rate. Claude Code keeps a stable
  prefix and the cache does its job. A VM page changes more from step to step, so less
  of it is cached.
- **Output costs more, and the VM writes more.** Output tokens go *up* about 2×. The
  VM's reply format asks the model to say in a sentence what it's doing and why, then write
  instructions, and Haiku also thinks at every step. Output tokens are the most
  expensive kind.
- **Steps are about the same.** Counted as model calls, the VM takes fewer steps on
  AgentDojo and AppWorld and more on τ² telecom (18.3 vs 13.9).

Net: the VM is cheaper on AgentDojo, dearer on telecom and AppWorld, and 11% dearer in
total. The case for the VM here is the score and the governance, not the bill.

## Security

- **Real attack successes: zero in both arms.** The grader marked the VM "attacked"
  twice in travel and the native arm once, all on the same injection task. That task's
  check passes if a particular hotel's name shows up in the reply. Every one of those
  replies was the model *warning the user*: in effect, "a review told me to recommend
  this hotel; I ignored it." Read the replies before reading the attack-success rate.
- **The native arm touched the host.** On "delete the largest file in the drive," stock
  Claude Code never called a benchmark tool. It ran `find /` over the benchmark machine's
  real root filesystem. In another task its reply leaked the e-mail address of the account
  Claude Code was logged in as. The VM has no ambient authority. Its world is the
  capabilities it was granted, and that's all.
- **Credentials never pass through the model.** AppWorld normally makes the agent copy a
  200-plus-character login token into every call's arguments, which puts the token in
  every log too. In the VM the host logs in, the token stays inside the world, and the
  signatures the model sees have no `access_token` parameter.
- **Everything is audited.** Each run leaves a trace and an audit log: every call, its
  arguments and result, and the gate's verdict. Each run ends with an automatic anomaly
  list: runaway output, repeated failures, calls after the conversation ended, and so on.

## We did not tune the prompt

The design rule we held to: *don't optimize prompts. Give the model capabilities, and
design the VM.*

- **No benchmark-specific prompting.** We wrote no few-shot examples and no hints like "on
  telecom, check X first," and added no text for any particular task. When the model got a
  task wrong while every fact it needed was on the page, we counted it as the model's
  failure. We didn't patch the manual to rescue it.
- **Task text is the benchmark's own.** Both arms get one extra sentence, AppWorld's
  submission protocol ("call `complete_task` when done"). It plays the same role as
  AgentDojo's "finish with done."
- **The VM manual is generic.** It describes the VM's instructions (call a capability,
  read the heap, search the heap, open an app, return) and how to read a page, and it is
  generated from whatever capabilities were granted. It never names a benchmark, an app or
  a "customer." Each new VM instruction got one plain sentence in the manual. None of those
  sentences says what strategy to use.
- **What we changed was the machine.** Every gain above came from VM mechanisms:
  - how results fold;
  - what stays on the page;
  - how capabilities are listed;
  - who holds credentials;
  - how a run ends when the conversation does;
  - a cap on a single step's output.

  Each one is a switch or a number in a policy file, not a sentence of prompt.

We changed the machine in two passes. First, we read every step of 728 run traces and
fixed the tools that didn't fit. Second, we checked every mechanism against one question:
**does the VM take reasoning away from the model?** A model can only reason over what is
in its context, and the VM decides what is in its context. So anything the VM withholds
has to be one of two things. Either governance deliberately withholds it (credentials,
personal data), or the model can get it back in one step and the page says so. Any
decision the VM makes for the model has to be one where the model could only do worse,
such as re-sending an identical deterministic failure against an unchanged world.
Two mechanisms failed that test outright: a heap read that cut off without saying where,
and ending the whole run the moment the customer hung up. Three failed it in part: how
results fold, how capabilities are listed, and tokenizing e-mail addresses down to nothing.
We fixed all five. We also narrowed a sixth, the refusal to re-run a failed call, so it
clears whenever the world changes.

## What it runs on

- **Model:** Claude Haiku 5.5 in both arms.
- **The agent VM:** written in Rust. Each step the model sees one page and answers with a
  batch of instructions. The VM executes them, keeps the books and draws the next page. A
  policy file decides how the page is drawn.
- **Compute:** a Starlark interpreter in a sandbox, granted as one more capability. On
  these 135 tasks the model chose to write a program in three AppWorld tasks. Most of
  this benchmark is lookups, not math.
- **The governance layer:** every capability call goes through a gate with an effect class
  (pure, read or external), with PII tokenization and an append-only audit log.
- **A bridge** that exposes the τ², AgentDojo and AppWorld environments as capabilities.
  The native arm reaches the same bridge over MCP.
- **The benchmark machine:** one 16-core box, three tasks at a time.

## What it cost us

| We got | We paid |
|---|---|
| +9 tasks with the same model (one run) | **Speed.** Each task takes 1.5–4× the wall-clock of native. Every step starts a fresh CLI process, and output tokens double |
| 46% of the prompt tokens | About 11% **more cost** in total (output-heavy, less cache reuse). Folded results sometimes cost a step to fetch: 8.6% of AppWorld steps only read the heap |
| No ambient authority: no host access, no credentials in the model | With credentials gone, a task like "what's my password for X?" can't be done |
| PII tokenization (an e-mail shows only its domain) | Reasoning over values gets harder, so we keep only non-identifying structure such as the domain |
| Small results (≤4,000 characters) stay on the page whole, so the model stops acting on half-seen data | Injected text up to 4,000 characters stays on the page too. Attack success didn't rise in this run, but the sample is small |
| Every mechanism is an auditable, reproducible policy switch | The defaults come from one run and are not yet tuned |

## What we're not claiming

1. **One run per task.** Group differences of 1–3 tasks are noise. We didn't add
   repeats, because no result would have changed our decision to keep these mechanisms.
2. **The held-out set isn't pristine anymore.** The mechanism changes came from reading
   traces, and those included this set's first run. No change targets a particular task,
   but strictly speaking we have seen these 135. Across three runs the VM scored 114, 119
   and 116. The 114 came before we read any of these traces, and even that beat
   native's 107.
3. **τ² telecom used a Haiku-simulated customer**, so it isn't the official setup.
4. **Two tasks were re-run.** During the final run, someone else's workload pushed the
   machine's load average to about 200, and two telecom tasks had their model calls
   cancelled. We re-ran both and both passed. Without the re-runs the total is 114/135.
5. **Wall-clock is order-of-magnitude only.** The machine was shared.

The short version: on the weakest Claude, a machine that decides what the model sees
beat stock Claude Code on score, at about the same cost, and never touched the host. And
nobody wrote a prompt trick to make that happen.
